# 개선한 C++17 Hex 탐색 엔진

**한국어** | [English](README.md)

이 구현은 기존 제출본과 별도로 제공하는 개선 버전입니다.
`deployment/agents/Group026/RAVE_TS.cpp`, 기존 실행 파일과 과거 경기 기록을
덮어쓰지 않습니다. 외부 라이브러리 없이 C++17 표준 라이브러리만 사용합니다.

## 빌드와 검증

```bash
g++ -std=c++17 -O3 -Wall -Wextra -Wpedantic -pthread native/hex_search.cpp -o hex-search
./hex-search --self-test
./hex-search --help
```

Windows의 MinGW에서는 출력 경로를 `-o native/hex-search.exe`로 지정하고
`native\hex-search.exe --self-test`를 실행합니다. 운영체제에 맞는 실행 파일을
빌드해야 합니다. 소스 빌드에는 호환되는 C++ 컴파일러가 필요합니다.

자체 검증은 3x3 보드의 모든 19,683개 색상 배치를 독립적인 BFS 연결 판정과
비교합니다. 또한 노드별 AMAF 갱신, 차례에 따른 승률 해석, 종료 상태,
즉시 승리와 방어, 내부와 목표 경계의 브리지 방어, 고정 시드의 재현성,
전체 탐색 횟수의 정확한 분배, 노드 상한과 시간 제한, 입력 검증을 확인합니다.
이는 구현의 정확성을 확인하는 검사이며 대국 성능을 증명하는 지표는 아닙니다.

## 입력 규약과 설정

기존 V2 입력 형식은 그대로 사용합니다.

```text
V2;R|B;board_size;START|CHANGE|SWAP;opponent_x,y-or-empty;comma-separated-rows;turn
```

보드에는 `0`, `R`, `B`만 사용합니다. RED는 첫 번째 좌표 방향의 두 경계를,
BLUE는 두 번째 좌표 방향의 두 경계를 연결합니다. 좌표는 0부터 시작합니다.
개선 엔진은 3x3부터 19x19까지 지원하지만, 공개 평가 결과에는 원래 조건인
11x11을 포함해 실제 평가한 보드 크기를 명시해야 합니다. 스왑 이후에는
매 요청에 명시된 현재 색상을 적용합니다.

기존 어댑터와 연결하기 위해 실행 파일 뒤에 `R|B BOARD_SIZE`를 지정할 수도
있습니다. 표준 출력에는 매 차례 `x,y` 하나만 기록합니다. 합법적인 스왑은
`-1,-1`로 표시합니다. 표준 오류에는 `hex_search_move` 형식의 JSON 진단
기록을 남깁니다. 잘못된 입력과 이미 끝난 보드는 `hex_search_error`를 남기고
종료 코드 2로 종료하며, 불법 수를 반환하지 않습니다.

```bash
./hex-search --policy rave_ts --seed 378 --workers 4 --iterations 10000
./hex-search --policy ts --seed 378 --workers 4 --seconds 0.5 --game-seconds 300
```

| 옵션 | 의미와 기본값 |
| --- | --- |
| `--policy` | `ucb`, `ts`, `rave_ucb`, `rave_ts`, 진단용 `legacy_ts`. 기본값 `rave_ts` |
| `--seed` | 음수가 아닌 기본 난수 시드. 기본값 378 |
| `--workers` | 독립적으로 탐색할 워커 수. 기본값 1, 최대 64 |
| `--iterations` | 한 수에 모든 워커가 합쳐 수행할 전체 탐색 횟수. 기본값 10,000 |
| `--seconds` | 한 수의 선택 시간 상한. 기본값 0이면 이 상한을 사용하지 않음 |
| `--game-seconds` | 한 에이전트가 한 경기에서 사용할 누적 선택 시간. 기본값 300초 |
| `--node-cap` | 모든 워커가 합쳐 할당할 노드 수 상한. 기본값 60,000 |
| `--memory-mb` | 트리 할당에 적용할 MiB 단위 예산. 기본값 128. 프로세스 전체 메모리 상한은 아님 |
| `--rave-k` | RAVE 혼합 계수의 기준값. 기본값 300. 0이면 선택에 AMAF를 반영하지 않음 |
| `--bridge` | 롤아웃의 브리지 방어 사용 여부. 기본값 1 |
| `--ordering` | 노드 확장 시 수의 우선순위 적용 여부. 기본값 1 |
| `--swap` | 중앙에 가까운 첫 수를 스왑하는 기존 휴리스틱 사용 여부. 기본값 1 |
| `--tactics` | 루트에서 즉시 승리와 상대의 즉시 승리 위협을 확인할지 여부. 기본값 1 |

`--seconds`만 지정하면 시간 제한으로 탐색을 제어합니다. `--iterations`도
함께 지정하면 먼저 도달한 제한에서 멈춥니다. 전체 횟수가 `I`, 워커가 `W`개면
각 워커에 `I/W`회를 배정하고, 앞의 `I%W`개 워커에 한 번씩 더 배정합니다.
즉시 승리, 방어와 스왑은 탐색 없이 결정할 수 있으므로 횟수 0과 별도 사유를
기록합니다. 상대에게 즉시 승리 수가 여러 개라면 하나를 막는다고 승패가
보장되지는 않습니다.

모든 워커는 전술 검사에 사용한 시간을 포함하는 공통 단조 시계의 마감
시점을 사용합니다. 반복마다 마감 시점을 확인하고 완료한 탐색만 집계합니다.
결과 집계 시간을 위해 짧은 여유 시간을 두지만 운영체제 스케줄링까지
정확한 시간 상한을 보장하는 것은 아닙니다.

노드 상한에 도달하면 새 노드를 만들지 않고 기존 노드와 롤아웃으로 탐색을
계속합니다. 따라서 메모리 상한 때문에 요청한 탐색 횟수를 임의로 바꾸지
않습니다. 워커별 진단 기록에 상한 도달 여부를 표시합니다. 루트만 만들 수
있는 작은 상한에서는 자식 통계가 없으므로 `node_cap_fallback`으로 표시합니다.

`START` 또는 이전보다 작거나 같은 차례 번호를 받으면 누적 시간 예산을
초기화합니다. 선택 시간에는 입력 해석과 전술 검사를 포함합니다. 평가 시에는
경기마다 새 프로세스를 실행하고 모든 시드와 설정을 기록하는 것이 좋습니다.

원시 네이티브 실행 파일의 `--rave-k` 기본값은 **300**입니다. Python CLI와 평가 목록은 명시적으로 **1000**을 사용하며, [선정한 설정](../reports/selection.json)도 `1000`입니다. 선정한 동작을 직접 실행하려면 `--rave-k 1000`을 지정하고, 평가에서는 고정 목록을 사용합니다.

## 통계의 의미

각 노드의 승리 수는 해당 노드에서 다음 수를 둘 플레이어의 관점입니다.
부모가 자식 수를 선택할 때는 자식의 승리 수를 반대로 해석합니다.
이는 자신의 차례와 상대의 차례에 모두 적용됩니다. 이미 승패가 결정된
노드는 확장하거나 롤아웃하지 않습니다.

RAVE 노드마다 수별 AMAF 방문 수와 승리 수를 따로 저장합니다. 갱신 대상은
그 노드 이후의 트리 탐색과 롤아웃에서 해당 플레이어가 둔 모든 수입니다.
아직 자식 노드로 생성하지 않은 수의 정보도 저장합니다. Hex에서는 한 칸에
한 번만 돌을 놓으므로 같은 후속 경로에서 한 수가 중복 등장하지 않습니다.
이렇게 하면 이미 둔 자식 수를 롤아웃에서만 찾던 기존 갱신 문제를 피할 수
있습니다.

RAVE의 혼합 계수는 `beta = sqrt(k / (3 * node_visits + k))`입니다.
해당 수의 AMAF 관측이 없으면 beta는 0입니다. RAVE-UCB는 Monte Carlo와
AMAF 승률을 혼합하고 자식 방문 수에 따른 UCB 탐험 항을 유지합니다.
RAVE-TS는 같은 beta로 성공과 실패 횟수를 혼합한 뒤 Beta(1,1) 사전분포를
적용해 표본을 뽑습니다. 이는 구현한 변형의 정의이며 모든 논문의 RAVE
공식을 그대로 재현했다는 의미는 아닙니다.

추가 정책인 `legacy_ts`는 같은 개선 엔진에서 사용하는 진단용 비교 조건입니다.
AMAF를 사용하지 않고 Monte Carlo 성공과 실패 횟수에
`child_visits / (1000 + child_visits)`를 곱해 기존 AMAF 미갱신 상태의
Thompson 표본 추출 효과를 반영합니다. 입력 처리, 시드와 시간 관리 등은
개선 구현을 사용하므로 기존 실행 파일 자체의 재현은 아닙니다.

## 재현할 수 있는 범위

워커 시드는 기본 시드, 보드 상태, 차례, 현재 색상과 워커 번호에서 결정합니다.
워커 번호 순서대로 집계하고, 최종 수는 방문 수, 승리 수, 작은 좌표 순서로
선택합니다. 같은 빌드와 설정, 요청 기록을 사용하는 고정 횟수 실험은 시간
제한이 탐색을 중단하지 않는 범위에서 재현할 수 있습니다. 워커 수가 바뀌면
난수 흐름도 달라집니다.

C++ 표준은 서로 다른 표준 라이브러리의 `shuffle`, 정수 분포와 감마 분포가
같은 난수 흐름을 사용하도록 요구하지 않습니다. 따라서 운영체제와 컴파일러가
다른 경우 수의 완전한 일치는 보장하지 않습니다. 시간 제한 실험도 장비와
스케줄링의 영향을 받습니다. 결과에는 운영체제, 컴파일러, 빌드 옵션, CPU,
워커 수, 탐색 횟수, 선택 시간과 상대 설정을 함께 남겨야 합니다.
