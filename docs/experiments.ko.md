# 실험과 측정 근거

**한국어** | [English](experiments.md) | [프로젝트 개요](../README.ko.md)

## 질문과 평가 범위

동일한 CPU 탐색 엔진에서 어떤 선택 정책이 강한가? 브리지 방어와 수 정렬, RAVE 가중치를 바꾸는 것이 개발 대진에서 개선을 보이는가? 전체 탐색 횟수를 맞춘 상태에서 루트 워커 수는 응답 시간과 메모리에 어떤 영향을 주는가?

이번 작업은 CPU 탐색, 정확성 수정, 대국 기록, 병렬 측정과 재현 도구를 다룹니다. 신경망을 다시 학습하지 않았습니다. 초기 Python 연구 코드, 초기 C++ 제출본과 과거 외부 상대 경기 이미지는 보존하며 서로 다른 근거로 설명합니다.

## 추가 최종 진단 실험

추가 실험은 첫 공개 결과 이후에 정의했으며, 별도의 시드와 대국 목록을 새
결과를 보기 전에 고정했습니다. 남은 검증 질문을 다루는 것이므로 이전 개발
절차를 바꾸거나 나중의 관측을 모두 독립적인 확증으로 설명하지 않습니다.
새 결과를 이용해 기본 정책을 다시 선택하지 않습니다.

| 목록 | 확인할 질문 | 경기 / 같은 장비의 교대 쌍 | 예산 |
| --- | --- | --- | --- |
| `configs/deep/shared-time.json` | UCB, TS, RAVE-UCB와 동일 조건의 초기 알고리즘에 대한 성능 | 400 / 200, 상대별 100경기 | 선수별 외부 경기 상한 300초, 워커 2개 |
| `configs/deep/tactical-ablation.json` | 스왑, 즉시 승리, 즉시 방어와 두 전술 검사의 효과 | 400 / 200, 제외 조건별 100경기 | 수당 전체 탐색 16,000회, 워커 2개 |

이전 개발 160경기, 최종 고정 횟수 256경기, 원본 시간 기준 4경기, 짧은 정책
시간 비교 48경기와 워커 비교 64경기는 **서로 다른 과거 532경기**로
보존합니다. 원래 목록, 원시 기록, 점수와 선택 결과를 유지합니다. 당시 소스
묶음으로 그 기록을 만들었던 실행기를 확인하므로 현재 코드로 과거 실행
환경을 바꾸어 설명하지 않습니다.

### 외부에서 배정하는 동일한 300초 경기 예산

![경기 시간 예산을 맞춘 결과](../assets/figures/ko/hex-shared-time.svg)

참가자와 경기의 조합 800개 모두에서 RSS를 측정했습니다. RSS는 측정한 프로세스 메모리이며 운영체제가 강제하는 메모리 상한이 아닙니다. 개선 엔진은 128 MiB 트리 예산에서 산정한 유한 노드 한도를 사용하고, 트리 확장이 한도에 도달해도 롤아웃을 계속합니다. 초기 알고리즘은 원래 메모리 할당 방식을 보존했습니다. 시간과 워커 한도는 같지만 메모리 관리 방식까지 동일한 비교는 아닙니다. 노드 한도 도달은 제한된 트리 확장을 의미하며 탐색 실패가 아닙니다. 초기 알고리즘 어댑터는 탐색 응답 2003개에서 원래 반복 횟수 한도 도달 여부를 기록했고 도달은 0회였습니다. 해당 어댑터는 워커별 노드 한도나 경과 시간을 계측하지 않습니다.

탐색 처리량은 네이티브 반복 횟수 합을 네이티브 응답 전체 경과 시간의 합으로 나누어 계산합니다. 병렬 워커의 경과 시간은 서로 겹치며 CPU 사용 시간이나 처리량 분모가 아닙니다. 서로 다른 장비의 시간과 메모리를 합친 통계는 결과를 설명하는 수치입니다. 동일한 장비에서의 직접적인 속도나 메모리 감소율로 해석하지 않습니다.

이 비교는 배포 알고리즘과 명시한 자원 설정을 비교합니다. 트리 표현, 난수
흐름, 초기 탐색 상한과 메모리 증가가 다르므로 전체 점수 차이를 AMAF 하나의
효과로 설명하지 않습니다. 과거의 원본 소스 4경기는 시간 관리가 다른 제한된
실행 확인이며 이번 평가를 대신하지 않습니다.

전체 원시 결과는 [공통 시간 집계](../reports/deep/aggregates/shared-time.json), [응답 및 자원 통계](../reports/deep/analysis/shared-time-costs.json), [경기별 기록](../reports/deep/evaluation/shared-time/)에서 확인할 수 있습니다.

### 전술 기능 제외와 실제 작동 횟수

![전술 기능의 개별 제외](../assets/figures/ko/hex-tactical-ablation.svg)

전술 400경기를 모두 완료했으며 실패와 미기록은 0건입니다.

| 제외한 기능 | 선정 정책 승리 / 완료 경기 | 완결 쌍 | 쌍 평균 및 95% 구간 |
| --- | ---: | ---: | --- |
| 스왑 판단 | 51 / 100 | 50 | 51.0%, 46.0–56.0% |
| 즉시 승리 검사 | 50 / 100 | 50 | 50.0%, 50.0–50.0% |
| 즉시 방어 검사 | 50 / 100 | 50 | 50.0%, 50.0–50.0% |
| 두 전술 검사 | 50 / 100 | 50 | 50.0%, 50.0–50.0% |

이 결과로 대국 우위가 확인됐다고 설명하지 않습니다. 세 즉시 검사 조건은
관측한 교대 쌍이 모두 1승 1패여서 쌍을 다시 추출해도 평균이 50%입니다.
50–50%라는 구간은 관측된 쌍 점수의 변동이 없다는 뜻이며 전체 상황의
정확한 승률이나 기능의 동등함을 증명하지 않습니다. 전체 수순이 일치한
쌍은 즉시 승리에서 48/50, 방어와 두 검사에서 각각 27/50이었습니다.
즉시 승리에서 달라진 두 쌍도 마지막 승리 좌표만 달랐습니다. 네 비교의
공통 일반 탐색 상태 7,407개는 기록된 워커 시드와 선택 수가 모두 같았습니다.

같은 보드와 차례 및 색상이 기록된 승리 상태 50개에서는 즉시 검사의
외부 응답 중앙값이 0.191ms, 일반 탐색은 231.654ms였습니다. 방어 상태
68개에서는 각각 0.256ms와 687.677ms였습니다. 일부 상태에서는 선택한
수도 다르므로 같은 입력의 조건부 응답 비용이며 전체 에이전트의 속도 향상
배수가 아닙니다. 전체 수의 응답 중앙값은 약 1.16–1.22초였습니다.
최종 진단 결과로 선정 정책을 다시 조정하지 않았습니다.

비교 조건은 `no_swap`, `no_win_check`, `no_block_check`, `no_tactics`입니다.
나머지 설정은 선정 정책과 같습니다. 경기별 기록에는 두 참가자의 실제
`pie_rule_swap`, `tactical_win`, `tactical_block` 판단과 외부에서 측정한
응답을 저장합니다. 작동 횟수와 응답 중앙값이 어떤 완료 경기를 집계했는지도
명시합니다.

네 비교는 서로 관련된 진단 실험입니다. 전술 상황이 드물면 승률 차이에
담긴 정보가 부족할 수 있습니다. 구간이 50%를 포함한다고 동등함이 증명되는
것은 아니며, 개별 구간이 50%를 벗어나더라도 여러 비교를 보정한 발견으로
주장하지 않습니다. 최종 진단 세트에서 가장 좋은 기능 조합을 다시 고르지
않습니다. 효과 기준을 통과하지 못한 선택적 후보는 기록하고 중단하며,
유리한 중간 점수를 이유로 이미 고정한 최종 경기 범위를 줄이지 않습니다.

고정한 11×11 상황별 검사에는 합법적인 Red-first 수순 45개와 정적 대칭 상태 16개인 총 61개 상태를 사용했습니다. 중앙, 경계와 모서리 시작, 즉시 승리와 상대의 단일 위협을 검사했으며, 488개 응답이 모두 통과했습니다. V2와 V3의 수와 판단 이유를 비교한 244개 조합이 모두 일치했고, 잘못된 입력 및 종료 상태의 거부 검사 4개도 통과했습니다. 정적 대칭 상태가 합법적인 선공 시작 대국 수순으로 도달 가능하다고 주장하지 않습니다. [상황별 원시 기록](../reports/deep/correctness/scenarios/receipt.json)은 기능과 프로토콜의 정확성 근거이며 대국 승률을 측정한 자료는 아닙니다. 검사를 끄더라도 일반 탐색으로 같은 수를 찾을 수 있습니다.

### 여섯 보드 상태의 워커 측정

![여섯 상태의 워커 비용](../assets/figures/ko/hex-worker-positions.svg)

Windows와 Kaggle Linux에서 같은 보드 해시를 사용해 각각 168회, 총 336회 탐색을 완료했습니다. 6개 상태에서 워커 1개, 2개, 4개, 8개를 각각 7회 측정했으며, 모든 요청의 전체 반복 횟수는 16,000회입니다. 환경별 총 2,688,000회, 두 환경을 합해 5,376,000회입니다.

각 요청은 새 네이티브 프로세스를 사용했으며, 설정은 고정된 순서로 측정했습니다. 요청부터 응답까지의 시간은 Python의 프로세스 생성 호출 시간을 제외하지만, 아직 진행 중인 네이티브 초기화 비용은 포함할 수 있습니다. 반복을 독립 트리에 나누면 탐색 경로와 반복당 연산량도 달라지므로 배수를 순수 병렬 효율이나 승률 향상으로 해석하지 않습니다. 7회 반복의 p95는 운영 환경의 지연 상위 구간을 정밀하게 추정하지 않으며, 이 결과로 선정 정책을 다시 조정하지 않았습니다. 원시 기록은 `reports/deep/benchmarks/windows.json` 및 `reports/deep/benchmarks/kaggle.json`에 보존합니다.

추가 벤치마크는 합법적인 Red-first 수순을 재생한 2번째, 41번째와 81번째
차례의 비종료 보드 세 개 및 각각을 전치하고 색을 교환한 비종료 정적 상태
세 개를 보존합니다. 교환한 정적 상태가 합법적인 Red-first 경기 수순으로
도달 가능하다고 주장하지 않습니다. 워커 1개, 2개, 4개, 8개가 동일한
전체 탐색 횟수를 완료하도록 하고, 스왑과 즉시 전술로 탐색을 생략하지 않도록
합니다. 장비마다 보드를 새로 만들지 않고 동일한 해시의 보드를 사용합니다.

상태와 장비별 외부 응답 p50 및 p95, 처리량, 반복 수와 최대 프로세스 RSS를
표시합니다. RSS는 네이티브 워커를 포함하며 Python 실행기는 제외합니다.
미측정 값은 null로 남깁니다. 과거 단일 보드의 시간도 이전 측정으로 보존하며
다양한 보드의 새 결과로 덮어쓰지 않습니다. 실행 중 CPU를 공유한 조건도
명시하고, 보이는 CPU 수만으로 물리적인 코어를 독점했다고 주장하지 않습니다.

### 공개 실행 도구와 과거 기록 재생

공개 CPU 도구로 생성한 패키지를 Kaggle에서 실제 실행했습니다. 내장 소스
추출과 확인, 개선 소스와 초기 소스 빌드, 유지 관리 검사와 원본 심판 및
어댑터 검사, ASan 및 UBSan 검사를 수행했고 선수별 상한 5초인 V3 대국
4경기를 완료했습니다. 이는 패키징 도구의 전체 실행 확인이며 성능 평가
400경기에 합산하지 않습니다.

최신 공개 도구 v3의 실행에서는 Python 테스트 107개를 건너뛰지 않고 통과했으며, C++ 자체 검증 15개와 sanitizer 프로토콜 검사 6개도 통과했습니다. 짧은 V3 대국 4경기는 모두 완료됐고 저장한 100수를 재생 검증했습니다. 별도의 중단 검증은 전체 400경기 목록의 첫 묶음에 40경기를 배정하고 평가 경기 시작 전에 멈춰 0경기를 기록했습니다. 이 중단 기록은 경기력 표본에 합산하지 않습니다. [공개 실행 문서](deep-runtime.ko.md)와 [한계](limitations.ko.md)에 범위를 구분했습니다.

이전에 저장한 532경기와 16,768수는 저장한 당시 소스로 재생 검증했습니다. 추가
릴리스의 검증기는 과거와 새 평가를 각각 실제 소스 및 실행기 기록에 연결해야
합니다. 저장한 수의 재생은 합법적인 변화와 기록된 연결 승리를 확인하며,
탐색 자체나 최적의 전략을 다시 증명하지 않습니다. 같은 작성자의 계정에서
다른 실행 환경을 이용했다고 독립적인 외부인의 검토라고 설명하지 않습니다.

## 사전에 고정한 절차

[실험 계획](../reports/study-plan.json)은 개발 결과 전에 고정했습니다. 개발 비교는 11×11 보드, 전체 워커 합계 수당 4,000회, 워커 2개, 노드 상한 100,000, 플레이어당 경기 제한 300초와 응답 제한 60초를 사용했습니다. 선후공 교대 쌍의 두 경기는 같은 시드와 강제 첫 수를 공유하며 같은 장비에서 실행했습니다. 로컬 Windows와 Kaggle CPU의 기록은 환경별로도 집계합니다.

| 평가 목록 | 목적 | 경기 / 선후공 교대 쌍 |
| --- | --- | --- |
| `development-policy` | 네 정책의 라운드로빈 | 96 / 48 |
| `development-features` | RAVE-TS의 네 가지 선택 가능한 변경 | 64 / 32 |
| `final-policy` | 선정 정책과 네 내부 비교 조건, 새로운 시드 | 256 / 128 |
| `final-time-reference` | 보존된 원본 소스를 다시 빌드한 실행 확인 | 4 / 2 |
| `supplemental-time-policy` | 같은 시간 예산의 정책 비교 | 48 / 24 |
| `supplemental-workers` | 같은 시간 예산의 워커 수별 대국 | 64 / 32 |

정책은 균형 대진의 완료 경기 점수로 선택합니다. 동점은 RAVE-TS, 그다음 명시한 정책 순서를 따릅니다. 선택 가능한 변경은 해당 후보 점수가 55% 이상이고, 쌍 단위 95% 부트스트랩 구간 하한이 50%를 **초과**해야 채택합니다. 실패한 후보는 더 튜닝하지 않습니다. 정확성 수정은 승률을 보고 되돌리는 선택 항목이 아닙니다.

선택한 정책을 자신의 최종 상대에서 제외하고 `legacy_ts`를 진단용 비교 조건으로 넣는 범위는 [최종 계획의 보충 기록](../reports/final-plan-addendum.json)에 있습니다. 선택, 최종 목록과 시간 기준 목록의 해시는 [선택 기록](../reports/selection.json)과 [고정 기록](../reports/final-freeze.json)에 남겼습니다.

| Kaggle CPU | 4 | 0.714 | 22,413 | 2.66× | 35.1 |
| Kaggle CPU | 8 | 0.683 | 23,412 | 2.78× | 32.7 |

처리량은 완료 횟수를 외부에서 측정한 응답 시간으로 나눈 값의 중앙값이며, 속도는 같은 장비의 1워커 처리량과 비교합니다. RSS는 반복 중 가장 큰 네이티브 프로세스 최고값이고 Python 실행기를 제외합니다. 워커별 트리 분배, 할당과 실행 경로가 달라져 RSS가 워커 수에 따라 반드시 증가하지는 않습니다.

Windows는 Python 3.12.7과 표시되는 논리 CPU 16개, Kaggle은 x86_64 Linux, Python 3.13.15와 표시되는 논리 CPU 및 affinity 4개를 기록했습니다. Kaggle의 `cpu.max=400000 100000`은 CPU 네 개에 해당하는 시간 할당이었습니다. 두 장비의 컴파일러와 처리 속도가 다르므로 장비 간 처리량을 알고리즘 개선 배수로 제시하지 않습니다. Kaggle에서 8워커가 4워커보다 조금 빨랐다는 관측도 모든 환경에 적용하지 않습니다.

이 표는 **단일 보드의 처리량 측정**입니다. 전체 경기의 평균 응답 시간이나 승률로 해석하지 않습니다. 워커 수별 대국 결과는 아래 별도의 시간 기준 실험에 있습니다. 원시 반복 측정은 [Windows JSON](../reports/benchmarks/windows.json)과 [Kaggle JSON](../reports/benchmarks/kaggle.json)에 제공합니다.

## 정확성과 보존 근거

Python 진단의 빈 3×3 보드, 1,000회 탐색에서 과거 RAVE 갱신은 0회였고 수정한 참조 구현의 AMAF 갱신은 13,772회였습니다. 독립적으로 합산한 갱신 수도 13,772회였습니다. 이 기록은 갱신이 작동하는지 확인하는 정확성 진단입니다. 승률 상승이나 처리 속도 개선의 근거로 사용하지 않습니다.

네이티브 자체 검사는 3×3의 모든 19,683개 색 배치를 BFS 연결성 판정과 비교하며 노드별 갱신, 상대 차례, 종료 상태, 전술과 자원 제한도 검사합니다. 원본 소스와 과거 경기 자산은 [보존 목록](../reports/baseline/original-source-inventory.json)에 고정했습니다. 결과 묶음의 검사와 새 대국 실행 방법은 [재현 가이드](reproducibility.ko.md)에 있습니다.

## 보존한 첫 릴리스의 검증 범위

앞서 정한 강화 계획은 같은 엔진에서 고정 횟수와 같은 시간 예산의 정책 비교, 워커 1 / 2 / 4 / 8개의 실제 승률도 요청했습니다. 개발 단계의 고정 횟수 비교와 단일 보드의 워커 처리량은 완료됐습니다. 최종 고정 횟수, 원본 시간 기준 확인과 추가 대국 목록은 각각 별도로 기록하며, 같은 시간 예산의 정책 대조와 워커 수별 대국 효과는 해당 추가 목록의 검증 결과로만 설명합니다. 선정한 정책은 변경하지 않습니다.
