# 실험과 측정 근거

**한국어** | [English](experiments.md) | [프로젝트 개요](../README.ko.md)

## 질문과 평가 범위

동일한 CPU 탐색 엔진에서 어떤 선택 정책이 강한가? 브리지 방어와 수 정렬, RAVE 가중치를 바꾸는 것이 개발 대진에서 개선을 보이는가? 전체 탐색 횟수를 맞춘 상태에서 루트 워커 수는 응답 시간과 메모리에 어떤 영향을 주는가?

이번 작업은 CPU 탐색, 정확성 수정, 대국 기록, 병렬 측정과 재현 도구를 다룹니다. 신경망을 다시 학습하지 않았습니다. 기존 Python 연구 코드, 기존 C++ 제출본과 과거 외부 상대 경기 이미지는 보존하며 서로 다른 근거로 설명합니다.

## 사전에 고정한 절차

[실험 계획](../reports/study-plan.json)은 개발 결과 전에 고정했습니다. 개발 비교는 11×11 보드, 전체 워커 합계 수당 4,000회, 워커 2개, 노드 상한 100,000, 플레이어당 경기 제한 300초와 응답 제한 60초를 사용했습니다. 선후공 교대 쌍의 두 경기는 같은 시드와 강제 첫 수를 공유하며 같은 장비에서 실행했습니다. 로컬 Windows와 Kaggle CPU의 기록은 환경별로도 집계합니다.

| 평가 목록 | 목적 | 경기 / 선후공 교대 쌍 |
| --- | --- | --- |
| `development-policy` | 네 정책의 라운드로빈 | 96 / 48 |
| `development-features` | RAVE-TS의 네 가지 선택 가능한 변경 | 64 / 32 |
| `final-policy` | 선정 정책과 네 내부 비교 조건, 새로운 시드 | 256 / 128 |
| `final-time-reference` | 보존된 원본 소스를 다시 빌드한 실행 확인 | 4 / 2 |
| `supplemental-time-policy` | 같은 시간 예산의 정책 비교 | 48 / 24 |
| `supplemental-workers` | 같은 시간 예산의 워커 수별 대국 | 64 / 32 |

정책은 균형 대진의 완료 경기 점수로 선택합니다. 동점은 RAVE-TS, 그다음 명시한 정책 순서를 따릅니다. 선택 가능한 변경은 해당 후보 점수가 55% 이상이고, 쌍 단위 95% 부트스트랩 구간 하한이 50%를 **초과**해야 채택합니다. 실패한 후보는 더 튜닝하지 않습니다. 정확성 수정은 승률을 보고 되돌리는 선택 항목이 아닙니다.

선택한 정책을 자신의 최종 상대에서 제외하고 `legacy_ts`를 진단용 비교 조건으로 넣는 범위는 [최종 계획의 보충 기록](../reports/final-plan-addendum.json)에 있습니다. 선택, 최종 목록과 시간 기준 목록의 해시는 [선택 기록](../reports/selection.json)과 [고정 기록](../reports/final-freeze.json)에 남겼습니다.

## 개발 정책 비교: 완료 96경기, 실패 0건

| 정책 | 승리 / 완료 경기 | 선택에 사용한 개발 점수 |
| --- | --- | --- |
| RAVE-TS | 44 / 48 | 91.7% |
| RAVE-UCB | 22 / 48 | 45.8% |
| 톰슨 샘플링 | 18 / 48 | 37.5% |
| UCB | 12 / 48 | 25.0% |

각 경기는 두 정책의 점수에 한 번씩 포함됩니다. 전체 96경기의 정책별 분모 합계는 192입니다. 이 점수로 **RAVE-TS를 선택**했으며 독립 최종 성능 추정으로 제시하지 않습니다.

| 왼쪽 정책 | 오른쪽 정책 | 왼쪽 승리 / 완료 경기 | 완료 쌍 | 왼쪽 점수의 쌍 단위 95% 구간 |
| --- | --- | --- | --- | --- |
| RAVE-TS | RAVE-UCB | 14 / 16 | 8 | 68.8–100% |
| RAVE-TS | 톰슨 샘플링 | 14 / 16 | 8 | 75.0–100% |
| RAVE-TS | UCB | 16 / 16 | 8 | 100–100% |
| RAVE-UCB | 톰슨 샘플링 | 9 / 16 | 8 | 25.0–87.5% |
| RAVE-UCB | UCB | 11 / 16 | 8 | 43.8–87.7% |
| 톰슨 샘플링 | UCB | 9 / 16 | 8 | 37.5–75.0% |

구간은 관측한 완료 쌍을 시드 378로 2,000회 재추출해 계산했습니다. 모든 관측 쌍을 이겼다면 비모수 구간이 100–100%로 축소될 수 있습니다. 이는 앞으로도 항상 이긴다는 보장이 아니며, 작은 개발 표본과 관측한 시작 조건의 범위를 벗어난 일반화 근거로 사용하지 않습니다. 경기별 Wilson 구간은 집계 JSON의 보조 지표입니다.

## 선택 가능한 기능 비교: 완료 64경기, 실패 0건

기준은 RAVE-TS, 브리지 사용, 수 정렬 사용, `rave_k=1000`입니다. 표의 승률과 구간은 **변경 후보가 기준을 상대한 결과**입니다.

| 변경 후보 | 후보 승리 / 완료 경기 | 후보 승률 | 쌍 단위 95% 구간 | 채택 |
| --- | --- | --- | --- | --- |
| 브리지 방어 제거 | 3 / 16 | 18.8% | 0–37.5% | 중단 |
| 수 정렬 제거 | 8 / 16 | 50.0% | 25.0–75.0% | 중단 |
| `rave_k=300` | 8 / 16 | 50.0% | 18.8–81.2% | 중단 |
| `rave_k=3000` | 12 / 16 | 75.0% | 50.0–100% | 중단 |

각 비교는 완결된 8쌍입니다. `rave_k=3000`은 점수는 높았지만 구간 하한이 정확히 50%여서 엄격한 기준을 통과하지 못했습니다. 수 정렬을 유지했다는 사실을 수 정렬의 개별 이득이 입증됐다고 설명하지 않습니다. 최종 설정은 개발 결과를 보고 추가 튜닝하지 않고 RAVE-TS, 브리지 사용, 수 정렬 사용, `rave_k=1000`으로 고정했습니다.

## 워커 처리량과 메모리: 측정된 결과

같은 11×11 보드에 Red가 `(0,0)`을 둔 뒤 Blue의 두 번째 차례를 검사했습니다. 스왑을 비활성화하고 수당 **전체 16,000회**를 1, 2, 4, 8워커에 나눴습니다. 시드는 378부터 반복별로 증가하며 브리지와 수 정렬을 사용했습니다. Windows는 7회, Kaggle은 5회 반복했고 모든 실행에서 정확히 16,000회를 완료했습니다.

| 장비 | 워커 | 외부 응답 중앙값, 초 | 외부 처리량, 회/초 | 1워커 대비 속도 | 최대 네이티브 RSS, MiB |
| --- | --- | --- | --- | --- | --- |
| Windows | 1 | 0.754 | 21,216 | 1.00× | 36.7 |
| Windows | 2 | 0.396 | 40,420 | 1.91× | 37.0 |
| Windows | 4 | 0.231 | 69,383 | 3.27× | 37.3 |
| Windows | 8 | 0.131 | 122,474 | 5.77× | 38.1 |
| Kaggle CPU | 1 | 1.897 | 8,436 | 1.00× | 35.6 |
| Kaggle CPU | 2 | 0.980 | 16,321 | 1.93× | 35.3 |
| Kaggle CPU | 4 | 0.714 | 22,413 | 2.66× | 35.1 |
| Kaggle CPU | 8 | 0.683 | 23,412 | 2.78× | 32.7 |

처리량은 완료 횟수를 외부에서 측정한 응답 시간으로 나눈 값의 중앙값이며, 속도는 같은 장비의 1워커 처리량과 비교합니다. RSS는 반복 중 가장 큰 네이티브 프로세스 최고값이고 Python 실행기를 제외합니다. 워커별 트리 분배, 할당과 실행 경로가 달라져 RSS가 워커 수에 따라 반드시 증가하지는 않습니다.

Windows는 Python 3.12.7과 표시되는 논리 CPU 16개, Kaggle은 x86_64 Linux, Python 3.13.15와 표시되는 논리 CPU 및 affinity 4개를 기록했습니다. Kaggle의 `cpu.max=400000 100000`은 CPU 네 개에 해당하는 시간 할당이었습니다. 두 장비의 컴파일러와 처리 속도가 다르므로 장비 간 처리량을 알고리즘 개선 배수로 제시하지 않습니다. Kaggle에서 8워커가 4워커보다 조금 빨랐다는 관측도 모든 환경에 적용하지 않습니다.

이 표는 **단일 보드의 처리량 측정**입니다. 전체 경기의 평균 응답 시간이나 승률로 해석하지 않습니다. 워커 수별 대국 결과는 아래 별도의 시간 기준 실험에 있습니다. 원시 반복 측정은 [Windows JSON](../reports/benchmarks/windows.json)과 [Kaggle JSON](../reports/benchmarks/kaggle.json)에 제공합니다.

## 정확성과 보존 근거

Python 진단의 빈 3×3 보드, 1,000회 탐색에서 과거 RAVE 갱신은 0회였고 수정한 참조 구현의 AMAF 갱신은 13,772회였습니다. 독립적으로 합산한 갱신 수도 13,772회였습니다. 이 기록은 갱신이 작동하는지 확인하는 정확성 진단입니다. 승률 상승이나 처리 속도 개선의 근거로 사용하지 않습니다.

네이티브 자체 검사는 3×3의 모든 19,683개 색 배치를 BFS 연결성 판정과 비교하며 노드별 갱신, 상대 차례, 종료 상태, 전술과 자원 제한도 검사합니다. 원본 소스와 과거 경기 자산은 [보존 목록](../reports/baseline/original-source-inventory.json)에 고정했습니다. 결과 묶음의 검사와 새 대국 실행 방법은 [재현 가이드](reproducibility.ko.md)에 있습니다.
